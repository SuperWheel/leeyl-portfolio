Overview

项目简介

我在 DeepSeek Harness（DSH）里把多个 AI CLI 当作子 Agent 使用时，遇到的问题很具体：每个 CLI 的对话散落在不同地方，谁在做什么、做到哪一步，很难追踪。动手之前，我横向调研了 herdr 等同类产品，看清楚这类工具各自怎么组织多个 Agent。

CLI Worker Now 把这些 CLI 接进 Harness：主对话负责派遣和接收结果，侧栏统一展示每个 Worker 的过程和状态。每个 Worker 有唯一的名字，可以套用角色预设；任务结束后，在主对话里点名就能接着做。CLI 仍使用各自的账号、模型和原生会话，插件只负责把它们组织起来。

Decision

方案转向：从自绘对话页到桥接原生会话

第一版能跑起来，但用下来发现方向不对。我没有在原方案上继续打补丁，而是重新评估后换了实现路线。

  1. 2026-10-04MVP：用 JSON 流式输出自绘对话页读取各 CLI 的 JSON 流式输出，在插件里自己画一套对话界面，先验证“主对话派遣 + 侧栏查看”这件事成立。
  2. 2026-10-06首个 Release v0.6.5第一个正式版本在 GitHub 开源发布。
  3. 使用中暴露的问题自绘页面越做越吃力问题集中在四点，见下方对照。
  4. 2026-10-18v0.8.1：改为桥接 Harness 原生会话参考 codex-host、Codingns4DSH 两个项目的做法，让每个 Worker 直接使用 Harness 原生的对话视图。

MVP · 自绘对话页

  • 难以还原 CLI 的工作状态：流式输出里的信息，拼不回 CLI 原本的工作过程。
  • 不能插入图片或文件：用户没法把图片、文件交给 CLI 读取。
  • 与原生对话页有差距：交互和观感总是和 Harness 自己的对话页差一截。
  • 维护负担大：每多一个功能，就要在自绘页面里再实现一遍。

v0.8.1 · 桥接原生会话

  • 界面交给宿主：子会话直接使用 Harness 的对话视图、输入框、模型与权限控件和“+”菜单。
  • 能力跟着原生走：图片和文件可以通过原生输入框交给 CLI，排队、停止和结束后续聊与原生一致。
  • 插件专注组织：插件只负责派遣、命名、角色、权限和状态汇总，不再重复造对话页。

What I did

我做了什么

  • 问题定义：从自己在 Harness 中把多个 AI CLI 当作子 Agent 使用时“对话分散、进展难追踪”的痛点出发，明确要解决的问题；前期横向调研了 herdr 等同类产品。
  • 需求与 PRD：与 AI Agent 协作撰写 PRD，梳理用户问题、功能范围、权限规则与验收标准；开发中用 OpenSpec 管理 22 份能力规格、164 条需求、527 个验收场景。
  • 方案决策：MVP 暴露问题后，评估自绘对话页的四个短板，决定改为桥接 Harness 原生会话，并随 v0.8.1 发布。
  • 组织 AI Agent 协作开发：把开发任务交给 AI Agent 执行，按能力规格和验收场景对照实现结果。
  • 发布与验收：从首个 Release v0.6.5 到 v0.8.4 共发布 10 个正式版本；v0.8.4 的 macOS 自动回归 4,702 项通过、0 失败，Windows 全量回归仍有失败项，单独记录、继续跟进。
  • 用户反馈与运营：按自身需求与外部 Issue 排期；7 个外部 Issue 全部关闭，从提出到关闭中位约 1 天；发布 5 篇介绍与教程，建立了用户交流群。
